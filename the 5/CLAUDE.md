# Project Overview: IEEE Micromouse Simulator & Telemetry Dashboard

Act as an expert Python/C++ developer and Machine Learning engineer specializing in Reinforcement Learning and embedded robotics. 

I am building a Micromouse simulator with a clean, multi-file Object-Oriented Programming (OOP) architecture. The mouse drives continuously (position in cm, heading angle, limited acceleration / speed, smooth corners), maps the maze only from noisy sensor distances, navigates with flood fill (Dijkstra for the fast route), and runs a full MMRC26 8-minute match: runs back to back, scored runs / best official time * 1000.

## Current Architecture
The project is split into 9 files (the 7 below plus `body.py`, the simulated physical robot - see "Drift & centering" - and `match.py`):
1. `config.py`: All constants: 10x10 grid (kept on purpose), real-world sizes (MMRC26: cells 18 cm INSIDE the walls, 1.2 cm walls, so `CELL_SIZE_CM` = 19.2 cm pitch; 7x7 cm mouse), the `SENSORS` layout (5 TOF, no IR since 2026-10-02: 80 cm / 85 % accurate / 25 ms per reading, describing the pose ~12.5 ms earlier - see "Hardware v3"), dropout, mapping evidence thresholds, motion limits, physics rate, sim speeds, Pygame colors. `CELL_SIZE` is the only drawing-scale knob.
2. `cell.py`: Defines the `Cell` class (walls, `walls_known`, visited status).
3. `maze.py`: Defines the `Maze` class: generates mazes that follow the MMRC26 rules (3-walled start cell open to the North, island 2x2 goal with one entrance, a wall on every post, loops); `rule_violations()` checks them all, including left/right wall-follower tests. Also BFS shortest path and least-turn Dijkstra. Wall keys ('H', x, j) / ('V', i, y) are shared with mapper.py.
4. `sensors.py`: `SensorArray.scan(px, py, theta)` casts each beam (numpy slab test) against real wall/post boxes and returns `Reading`s carrying ONLY a noisy distance (+ where the sensor is/points). No ground truth (which wall was hit) leaks out.
5. `mapper.py`: `Mapper` turns readings into per-edge evidence scores: beam end on a wall face = wall vote, beam passing a slot = open vote, driving through = certain open. Ambiguous hits (posts, corners) and one-sample dropouts are ignored; the "too close to a post" margin grows with beam length (`POST_MARGIN_PER_CM`). An edge is known at |score| >= `WALL_EVIDENCE_THRESHOLD`.
6. `micromouse.py`: The `Micromouse`: `update(physical_maze, dt)` per physics tick. Senses at `SENSOR_HZ`; always brakes towards a target cell centre and, near the braking point, decides: straight on through a confirmed-open edge (target extends, no stop) or stop at the centre and turn in place. Only ever drives through confirmed-open edges. Runs restart by hand-placing at the start (`begin_run`). Official timing (rule 6.1.f): the run clock starts when the REAL body's front edge crosses the start line (start cell's north edge) and stops at the goal entrance - `_check_timing_lines`. So the mouse lines up `START_BACKOFF_CM` (2.8 cm) back in the start cell for a flying start, and does not brake for the finish: it crosses the entrance at full speed and stops deeper inside the goal room. `self.runs` is one dict per run (mode, official time, cells, crashed, returned). Between runs the mouse is CARRIED back by hand (user's choice): `AUTO_RETURN = False`. With it True, run phases are TO_GOAL -> TO_START (it drives itself home at `HOME_SPEED_CM_S` 45 cm/s, untimed, still mapping; flood fill retargets via `nav_cells`) -> park (face North, reverse `START_BACKOFF_CM` by shifting the believed pose) -> run over. A self-returned run keeps its real pose (`_place_at_start(by_hand=False)`); only a carried/rescued run gets a fresh placement error.
7. `match.py`: `Match(maze, kind)` - two kinds, picked with the purple "Mode" button (switching restarts on the same maze): "THREE_RUNS" = 3 chances start->goal, each started with the Start button like the original 3-round system (the last one races the best confirmed route: `begin_run(last_chance=True)`); "MATCH" = one 8-minute window (rule 6.1): begin run -> mouse drives -> run ends (parked at home, or crashed) -> pause (`AUTO_RESTART_S` 0.5 s if it drove itself home, `HANDLING_TIME_S` 8 s if carried, `RESCUE_TIME_S` 12 s after a crash) -> next run, until the clock runs out. Holds `times`, `best_time`, `score`, `time_left`.
8. `main.py`: The `DashboardApp` Pygame UI: "The Maze" (ground truth), "Running Maze" (the mouse's map, sensor hit point cloud, live beams), right sidebar with on/off overlay buttons + run stats + sensor readings, blue Regenerate / Start buttons at the bottom. Up/Down arrows change sim speed (x0.25 - x8).

Validation used so far: headless runs over 200 random mazes -> 0 collisions, 0 wrongly-mapped edges, 0 failed rounds.

## Drive train & strategy
Two wheels on the body's centre line, 34 mm wheels (34 -> 44 -> tried 66 -> 44 -> back to 34 mm on 2026-10-02), motors 400 rpm at the wheel -> top speed ≈ 71.2 cm/s. Corner speeds come from `corner_speed(r)` = min(outer wheel at full rpm, tyre grip `MAX_SIDEWAYS_G` 0.5 g): 52 / 57 / 60 cm/s for radius 9.6 / 14.4 / 19.2 (all rpm-limited). Diagonal straight at full speed. NO encoders, BMX055 IMU (since 2026-10-04, see "Hardware v4"). Accel 200 cm/s² and wheel track 7 cm are assumptions (in `config.py`). Speed: full rpm everywhere (search runs too, through cells already mapped; `EXPLORE_SPEED_CM_S` 40 cm/s only when heading into a cell whose walls aren't all confirmed). Steering gains CENTER_KP 1.2, CENTER_KH 14. Rounds: SEARCH (flood fill) until the map proves the best route, then FAST (Dijkstra quickest route over confirmed-open edges, cost = cell time + corner time, U-turn = pivot time; re-plans if the map changes). The last round is always FAST. Keep the bot logic small and C++/ESP32-portable (user request). Strategy notes from the rulebook (score = runs / best time): see the chat plan - smooth turns first, then official timing / flying start / match mode.

Turns: corners are SMOOTH quarter circles (motion "ARC") of radius half a cell (`TURN_RADIUS_CM` 9.6) centred on the corner post, from the entry-edge middle to the exit-edge middle, without stopping, at `CORNER_SPEED_CM_S` (outer wheel at full rpm). The move is decided at `_decision_distance()` before the target cell; an arc needs the exit edge confirmed open. Arcs are tracked on the encoder-dead-reckoned pose (`_arc_omega`: radius + tangent feedback) and start/end `MOTOR_LAG_COMP_S` early. Pivot turns on the spot remain only for U-turns / dead ends / unconfirmed exits. Fast run went from ≈8.2 s (pivots) to ≈3.6 s (40/45 cm/s corners) to ≈3.5 s at full 381 rpm; round 1 search ≈7.2 s.

## Fast-run geometry (2026-09-24)
Arcs are generic (`_begin_arc(plan)`: start point, centre, radius, side, sweep, speed, then) and `_plan_fast_path()` marks cells on the fast route at the start of each FAST run:
- BIG corner (`BIG_CORNERS`): a lone corner with straights before and after -> radius `BIG_TURN_RADIUS_CM` 14.4 (outer-wheel limit ~54.5 cm/s vs 49.7; inner post clears the body by 2.8 cm).
- DIAGONAL (`DIAGONALS`): 2+ corners in a row alternating left/right, straight before and after -> 45-degree curve (`DIAG_TURN_RADIUS_CM` 19.2, ~57 cm/s) onto a straight line through the edge middles (motion "DIAG", `_diag_step`, pursuit on the 2-D dead-reckoned pose; `_observe_2d` fixes position from ANY known wall/post face + heading via `DIAG_HEAD_GAIN`), 45-degree curve back into the lane. Posts pass only ~1.9 cm from the 8 cm body.
- Hero strategy (`DIAG_HERO_ONLY`): diagonals are used only until one diagonal run reaches the goal (sets the best time), then it races without them.
Results, 24 full matches: neither 14,652 (best 2.72 s, 4.8 % crash); big only 15,044; diagonals always 15,049 (best 2.50 s but 11.3 % crash); big + hero diagonals **15,796** (best 2.53 s, 6.3 % crash). Diagonal crashes come from ~1-2 cm position / few-degree heading errors at entry that the 1.9 cm margin can't absorb; speed (45-60) and stronger gains don't change it.

## Start placement (2026-09-24)
- Start corner is random per maze (`RANDOM_START_CORNER`, `START_CORNERS`, rule 5.c): bottom-left opens N, top-left E, top-right S, bottom-right W (the next cell clockwise). `Maze.start` / `Maze.start_opening`; `Micromouse(start, start_heading)`; everything that assumed (0, 9)/'N' now uses them. The start cell's 3 walls are put in the mouse's map from the rules (`Mapper.mark_wall`).
- Hand placement is a random spot in the start cell (`START_SPOT_SIDE_CM` 4, `START_SPOT_ALONG_CM` 3, `START_ANGLE_ERROR_DEG` 8); the firmware only assumes "centre, facing the opening". Before moving it stands `ALIGN_TIME_S` 0.2 s (untimed) and (a) least-squares fits offset + heading to side readings of the start walls at different distances ahead (IR ~0.5 cm, diagonal TOFs ~8 cm) - `_fit_start_pose`; (b) on fast runs, averages the front TOF against the known first wall ahead to fix how far forward it sits. Big corners / diagonals wait until the along position has been fixed (`along_fixed`).
- Results (20 matches): fixed start 16,410 / 0 % crash / best 2.55 s -> random spot without fixes ~13,000 / 15.5 % -> now 14,888 / 1.4 % / best 2.71 s. Tried and REMOVED: side-IR wall-edge (post) detection for along position - correct for big errors but jittery (+-0.3 cm per 5 ms IR sample) and fooled by cross walls; net worse. Diagnosis tool: placement side/angle errors mattered more than along ones before the least-squares fit.

## Drift & centering (reality gap)
`body.py` is the TRUE robot (simulation only): motor lag (`MOTOR_TAU_S` 30 ms), open-loop motor speed errors, wheel slip, hand-placement error, TOF readings that describe the pose `SENSOR_LATENCY_S` (20 ms) ago. Since 2026-10-04 `body.step()` returns only the GYRO reading (until then: encoder counts); the firmware (`micromouse.py`) builds its believed pose from the gyro + its motor model (`_odometry`) and places each reading at its believed pose 20 ms ago (`pose_hist`). Localisation (`_observe_walls`): every TOF reading up to `MAP_TRUST_CM` (25 cm) is compared with a ray-cast of the mouse's CONFIRMED walls from the believed pose (`SensorArray(memory, known_only=True)`); a wall along the lane corrects the observer (offset, heading, learned wheel curve), a wall across the lane corrects the along-lane position; posts / unexplained readings are skipped. Side-looking sensors (±90°, now TOFs) are used directly against the wall line beside the body with a WIDE 6 cm gate (see "Hardware v3"). Front-wall re-centring (averaged front TOF) at every stop / after every pivot. Any body point inside a wall/post = crash (round lost).
Match results (20-40 full 8-minute matches): best official run ~2.70 s avg (vs 3.46 s wall-to-wall: the run-up and the stop in the goal are not timed), ~37-39 scored runs per match. Score avg ~14,300 carried back by hand (6.5% of runs crash) vs ~14,400-15,200 driving itself home (23-26% of runs crash - twice the distance per scored run, and each crash costs a rescue). Score is a wash TODAY; self-return would win once crashes drop. The user chose hand-carrying (`AUTO_RETURN = False`). Slower home speed (30) trades too many runs: worse score. NOTE: `START_BACKOFF_CM` 3.5 cm doubled crashes (tail 0.5 cm from the back wall + placement error) - 2.8 is the safe value.
Measured (headless, 200 rule-compliant mazes / 600 runs, no IMU, full 381 rpm): ≈6.5% of runs crash, 0.66 cm RMS off-centre. Higher speed alone raised crashes (fewer readings per cm, lag/latency cost more distance); stronger steering gains brought it back. Stronger OBSERVER gains go unstable - don't. Noise-source test (200 mazes): removing the wheel-size mismatch halves crashes (39 -> ~23); slip, placement and TOF noise barely matter. Most crashes are the 2nd corner of a back-to-back pair after drifting through wall-less stretches. Tried and REJECTED (same seeds, all worse): slower chained corners (35-45 cm/s), arc curvature from measured speed, earlier decisions, learned curve inside arcs. Fix is calibration / hardware (IMU, longer side IR). SECOND crash cause (fixed): corners committed through side walls the map wrongly had as OPEN (19 of ~3000 corners; straights: 0). Wrong open votes came from real hits placed at a slightly wrong pose, mostly while rotating. Fixes: no mapping during ARC/TURN; open needs -OPEN_EVIDENCE_THRESHOLD (8) vs wall +3; 'drove through' is a -DRIVEN_VOTE (8) vote, not an override. Result: 4% of runs crash (was 6.5%), round-1 search ~9.9 s (was 7.2, more look-stops), fast run unchanged ~3.5 s. Diagonal runs through staircases were requested and are the next feature (paused to investigate crashes): diagonal clearance to posts is only ~1.9 cm per side. Most remaining crashes are corners taken in open areas (no walls to localise on for >1 s). Tried and rejected (no gain): an IR steer-away reflex during arcs, longer trust ranges, stronger along gain. The real fixes are hardware: an IMU and/or a longer-range side IR.
Dashboard: The Maze shows the REAL body + its path (cyan, "Real Path"), red on crash; Running Maze shows the BELIEVED pose (incl. observer estimates).

## Sensor realism (user's spec, 2026-09-24)
TOF: 25 ms per reading (`TOF_MEASURE_S`, 40 Hz), value = average over that window so `latency` = 12.5 ms; 85 % accurate = 95 % of readings within +/-15 % of the true distance (`noise_sigma`: sigma = (1-accuracy)/2 * distance). IR: range 3.5 cm, 95 % accurate, sampled every 5 ms, no latency. Sensors of one kind are read together on their own timer (`SENSOR_GROUPS`, `_sense(maze, kind)`); body/firmware pose histories give each kind its own latency. Result (150 mazes x 3 runs): crashes 25 -> 11 of 450, wrong map edges 38 -> 14, round-1 search 9.1 -> 10.1 s, fast run unchanged 2.76 s; 20 full matches: score ~14,400, 5.2 % of runs crash. What helped is the IR: range 2.5 cm alone -> 35 crashes, IR read every 25 ms -> 20. The noisier TOF only slows mapping. Interpretation note: "85 % accurate" was modelled as +/-15 % error; if it means "15 % of readings are wrong", add outliers instead.

IR range study (2026-09-24, 150 mazes x 3 runs / 20 matches): 3.5 cm -> 30/450 crashes, match 15,587 (6.8 % crash); 5.0 -> 14; 6.5 -> 10/450, match **16,410 with 0 % crashes**; 8.0 -> 4/450, match 16,240. Above 5.5 cm the IRs see both side walls continuously. Even at 8 cm, diagonals on every run (DIAG_HERO_ONLY=0) still cost score (15,802, 5.2 % crash) - keep the hero rule. The user chose 6.5 cm; config now uses it.

## Hardware v3 (user's sketch, 2026-10-02): 7x7 body, 34 mm wheels @ 400 rpm, 5 TOF, no IR
The real digital IRs (0/1, hand-calibrated, light-sensitive) were dropped. 5 TOFs, all in the front half, 1 cm in from the edges (`config.SENSORS`, body frame x right / y forward): Left (-2.5, 1.0, -90°), Front-Left (-2.5, 2.5, -45°), Front (0, 2.5, 0°), Front-Right (2.5, 2.5, +45°), Right (2.5, 1.0, +90°). Side y = 1.0 (2.5 cm behind the front edge) and the 45° angles were read off the sketch - confirm with the user. Centred, the side TOFs read 6.5 cm, front TOF 6.5 cm to a front wall, diagonals ~9.2 cm to the side walls.
- Firmware change: the "use directly" side path is now chosen by geometry (|sin angle| > 0.99), not sensor kind. Tested alternatives, all worse: side TOFs through the map ray-cast path 79/450 crashes, direct path with a 2 cm gate 31/450, vs 13/450 with the 6 cm gate (after corners the estimate is often 2-6 cm off and the side walls must be allowed to pull it back). A slanted side beam slipping past a post through an opening can read e.g. 10 cm and pass the gate; a "reject a 2 cm jump between samples" filter fixed that case but made no measurable difference (1200 runs), so it was removed.
- Mapper: far side/front TOF hits (36-45 cm) on posts were being voted onto the slot beside the post (heading error moves a far hit along the wall). `POST_MARGIN_PER_CM` 0.05 cut wrong edges 14 -> 5 per 150 mazes.
- Results (same seeds; old = 44 mm/381 rpm/7x10/side IR): 400 mazes x 3 runs: crashes 54 -> 34 of 1200, search run 9.83 -> 9.53 s, fast run 2.04 -> 2.44 s. 88 matches: score 21,511 -> **16,854**, best run 1.99 -> 2.40 s, crash 2.7 -> 3.9 %. The score drop is mostly the 19 % lower top speed. Crashes moved from straights (57 -> 31) to corners (42 -> 104): the side TOFs give a noisier offset/heading at 40 Hz with 12.5 ms latency instead of the IR's clean 200 Hz, and arcs are driven blind on the encoders, so entry errors carry through. Observer gain sweep (heading 0.01-0.06, offset 0.2-0.5): stronger is worse, weaker within noise - kept 0.3 / 0.02. The real fixes remain an IMU (gyro) for arcs, or faster/cleaner side ranging.

## Hardware v4 (2026-10-04): BMX055 IMU, NO wheel encoders
The user removed the encoders and added an IMU. What the firmware knows now:
- **Turn:** gyro z (`body.Gyro`: per-robot offset ~N(0, 1 °/s) that random-walks 0.01 °/s/√s, noise 0.15 °/s per 5 ms reading, ±1 % scale, clipped at `GYRO_RANGE_DEG_S` 1000).
  - These are BMX055 datasheet-class values (offset ±1 °/s, sensitivity ±1 %, 0.014 °/s/√Hz at the 116 Hz filter).
  - Measured peak turn rates: pivots 761 °/s, arcs 441, steering 325.
  - Range ±1000 is identical to no clipping. ±500 drops to 15,617 / 5.8 % crash (vs 16,324 / 3.8 %).
  - Tell the user: set ±1000 or ±2000 °/s on the chip. The offset is measured in the start cell during the 0.2 s alignment (`gyro_sum` / `gyro_count` -> `gyro_bias`), every hand-placed run.
- **Distance:** no sensor. A motor model `v_model` (command through the `MOTOR_LAG_COMP_S` lag) times a learned `speed_scale`. The real motors run open loop: `MOTOR_SPEED_ERROR` 4 % common, `MOTOR_MISMATCH` 2 % left/right, per robot.
- **Speed learning** (`_observe_walls`, wall-across-the-lane branch): `speed_scale -= SPEED_LEARN (0.0005) * innovation * u_fwd`, clamped to ±20 %. "Always further along than predicted" means the motors are faster than modelled. It converges from ~3.2 % to ~1 % error in about 10 runs. Learning 4x faster at first (`fastlearn`) was not better.
- **Removed:** the learned wheel-mismatch curve (`est_curve`, `OBS_K_CURVE`, `DIAG_USE_CURVE`). The gyro sees the real rotation directly.
- **Pivot settle:** waits for the gyro turn per tick < 1e-4 rad.
- **Dashboard:** "Motor speed: learned X % (real Y %)".
- **Diagnosis** (400 mazes x 3 runs): no learning 193/1200 crashes. With the motor speed error at 0: 34 (= the encoder version). Mismatch 0: 172. Perfect gyro: 165. So the unknown motor speed (along-corridor position) is THE problem; the gyro is fine.
- **Ceiling with the speed known exactly:** 88 matches, 17,124 / 2.5 % crash. That is better than encoders (16,854 / 3.9 %) because the gyro fixes corner heading.
- **`BIG_CORNERS` now False:** big corners start a cell early and need an exact along position. Same score (16,324 vs 16,322), crashes 6.5 -> 3.8 %. `ALONG_GAIN` 0.3 / 0.4: no gain.
- **Final** (88 matches): score **16,324**, best run 2.47 s, 3.8 % of runs crash. 400 mazes x 3 runs: 81/1200 crashes (encoders: 34). Only 3 runs leave little time to learn the speed. Wrong map edges 136 vs 18, mostly from along errors before the speed is learned.
- **Sensitivity to motor calibration** (88 matches): ±2 % -> 16,600 / 2.5 %; ±4 % -> 16,324 / 3.8 %; ±8 % -> 14,170 / 12.8 % (some matches score 0: a robot ~10 % off crashes every search run before it learns). Tell the user: calibrate PWM -> speed, and compensate for battery voltage.
